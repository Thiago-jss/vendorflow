# Identity and Organization Persistence

**Status:** Implemented foundation
**Last updated:** 2026-08-30
**Scope:** Organization, Branch, Department, User, and current role membership

This document makes the first implementation of ADR-002 concrete. It does not introduce
authentication, credentials, sessions, route authorization, identity-management CRUD, or
procurement data.

## Model

```text
Organization (tenant)
  └─ Branch
       └─ Department
            └─ User
                 └─ UserRole (current fixed-role assignments)
```

Every Branch, Department, User, and UserRole row carries `organization_id`. Department also
carries its Branch identity. User carries both Branch and Department identity, and the
database requires that the Department belongs to that exact Branch and Organization.

Organization is the only tenant. Branch and Department remain responsibility and structure
scopes inside it.

Users have an `is_active` flag because FR-004 requires deactivation without deletion.
Deactivation enforcement belongs to authentication and identity-management use cases; the
current-organization query already excludes inactive users. No generic soft-delete fields
were added to other tables.

## Role membership decision

The persistence model uses a normalized `user_roles` assignment table with the fixed
PostgreSQL enum values `EMPLOYEE`, `MANAGER`, `BUYER`, `FINANCE`, and `ADMIN`.

The alternatives were:

- A single role column cannot represent FR-006 or the existing `TrustedPrincipal.roles`
  contract, because a person may be both Manager and Buyer.
- An enum array can represent several values but makes individual grants/revocations,
  duplicate prevention, relational querying, and later audit facts less explicit.
- A normalized assignment makes one grant one row. Its composite primary key
  `(organization_id, user_id, role)` prevents duplicate membership, and its composite
  foreign key proves that the User belongs to the same tenant.

The normalized relation is therefore the smallest model consistent with current product
requirements. Roles are still a fixed enum; custom role definitions remain outside MVP.
PostgreSQL prevents duplicate assignments but cannot express "at least one child row" with
a simple foreign key. The future user-management operation must create the initial role in
the same transaction and refuse to revoke a User's last role.

## Identifier and timestamp strategy

All durable entity identifiers are PostgreSQL UUID values generated by
`gen_random_uuid()`. This gives opaque, globally collision-resistant UUIDv4 identities,
works in the supported PostgreSQL version without a new application dependency, and also
works for writes outside Prisma. UUIDv7 was not selected because neither the current
dependency set nor a stated query requirement justifies adding generation machinery.

Organizations, Branches, Departments, and Users have `created_at` and `updated_at` as
timezone-aware timestamps. Role assignments have `created_at`, which records when the
current membership row was granted; they do not need an update timestamp because the role
value is part of the assignment identity.

## Business uniqueness

The implemented business keys are:

| Concept           | Constraint                           | Reasoning                                                                                                     |
| ----------------- | ------------------------------------ | ------------------------------------------------------------------------------------------------------------- |
| Organization name | none                                 | No product rule says customer display names are globally unique.                                              |
| Branch name       | `(organization_id, name)`            | Duplicate names inside one tenant are ambiguous; different tenants may use the same name.                     |
| Department name   | `(organization_id, branch_id, name)` | A name is unique in its Branch and may repeat in another Branch.                                              |
| User email        | `(email)`                            | Globally unique so authentication can resolve User first and derive Organization from the persisted identity. |
| Role membership   | `(organization_id, user_id, role)`   | The same role cannot be granted twice to the same User.                                                       |

Branch and Department name scope is the smallest reasonable assumption where the product
requirements do not state explicit uniqueness. Changing display-name rules later does not
change entity identity because references use UUIDs. Branch and Department uniqueness uses
PostgreSQL's exact, case-sensitive text comparison because the product defines no casing or
locale rule; identity-management inputs can adopt a stronger normalization rule later.

User email remains lowercase and trimmed by a PostgreSQL check. The client will not provide
`organizationId` as authentication authority. If one human later needs membership in
multiple Organizations, the model should evolve to one global User identity plus
Organization Membership rather than creating duplicate Users with the same email.

## PostgreSQL tenant constraints

Tenant-owned parents expose candidate keys such as
`UNIQUE (organization_id, id)`. Relationships then carry the same tenant value on the child
and reference the candidate key, for example:

```sql
FOREIGN KEY (organization_id, branch_id)
  REFERENCES branches (organization_id, id)
```

Department uses that key to prove its Branch is in the same Organization. User goes one
step further:

```sql
FOREIGN KEY (organization_id, branch_id, department_id)
  REFERENCES departments (organization_id, branch_id, id)
```

Consequently, a User labelled as Organization A and Branch A cannot point at a Department
from Organization B or even at a Department from another Branch in Organization A. The
same pattern protects UserRole→User. Direct Organization foreign keys remain present on
every tenant-owned table, and all delete/update actions are restrictive rather than
cascading away identity or structural history.

## Application and persistence boundary

`identity-access` owns the first tenant-scoped persistence port and its Prisma adapter. The
public persistence criteria always require `organizationId`; there is no
`findBranchById(id)` operation. Single-branch reads use the compound
`(organization_id, id)` selector, and lists put `organization_id` in the database predicate.

`GetCurrentOrganizationContext` is the first application capability. It accepts only a
`TrustedPrincipal`, derives both organization and user identity from that principal, and
returns the persisted Organization, Branch, Department, and authoritative role membership.
It performs one scoped lookup and returns the same application error for foreign, missing,
inactive, or missing-tenant membership. There is intentionally no HTTP endpoint until real
authentication can bind the principal; no client-controlled header substitute was added.

## Migration reasoning

The historical bootstrap migration is unchanged. The new forward migration creates the
identity enum and tables, adds candidate keys, business uniqueness, checks, and foreign
keys, then drops `platform_metadata`. On a fresh database, Prisma first creates and then
drops the bootstrap table. On a database that already applied the bootstrap, the new
migration drops the existing table. Both paths therefore converge on the same schema while
preserving migration history.

## PostgreSQL integration tests

The API test harness starts an isolated PostgreSQL 17 Testcontainer, sets its connection URL
only for the test process, applies the real Prisma migration history, and exposes the shared
database service. Tests clean identity tables in dependency order between cases and stop the
container afterward. The harness is intentionally small so future procurement, outbox,
authorization, and concurrency suites can extend it without inheriting a generic testing
framework.

The initial two-tenant fixture creates Organization, Branch, Department, User, and two role
assignments for both A and B. Tests prove scoped reads and lists, global email uniqueness,
tenant-aware structural uniqueness, equal foreign/missing behavior, and PostgreSQL rejection
of cross-tenant hierarchy, membership, and role relationships.
